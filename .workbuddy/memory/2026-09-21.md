## 只读诊断：「Agent 接管效果差 + 一次执行命令过多」（未改代码）

证据：截图模型 Qwen3.5-4B，5 步 98.7s、压缩 249.1s、52.0k tok。模型每轮把 4 个 grep 变体用 `;` 压成一行下发（step3/4 失败、step5 成功）。

读代码定位到 4 处机制缺口（都能在代码里对上号）：

1. **所有闸门都要求「已成功」，失败命令完全在盲区。** `createDupTracker` 只读阈值 `n>=2 && lastOk`、写 `n>=1 && lastOk`；`dupReason` 族计数同样是 `n>=2 && lastOk`。step3/4 都失败 → `lastOk=false` → 同族变体第 3 次也不会被拦。唯一能抓失败的 `createFailTreadmill` 要求**连续 2 次错误签名完全相同**（`errorShapeOf` 归一化后），签名一变 `streak` 就重置为 1 → 永不触发。净效果：只剩 `MAX_AGENT_STEPS=20` / `TASK_TIMEOUT` 兜底。
2. **`AGENT_MAX_SUB_COMMANDS_PER_LINE=8` 按「段」计数，管道链不算。** `splitCommandParts` 只按顶层 `;`/`&&` 拆，`cat X | grep A` 记 1 段 → 一行 4 条管道链稳稳在 8 以内。
3. **观察粒度 = 命令行，不是子命令（最核心）。** `extractResult` 剔除 `:seg:` 打点后只留 `segmentStatus`（序号+退出码），**段的输出边界被丢掉**；`buildObservation(entries)` 的 entries 来自 `parsed.commands`（按行）→ 一行 `;` 串联只有 1 个 entry → `total=1` → 8000 字符预算全给这一条 blob → 模型无法归因「哪几行是哪个 grep 的」→ 判断不出「grep 没匹配到」→ 换 pattern 重发。
4. **`focusOutput` 无错误关键词时退化成 `text.slice(0,budget)` 纯前 N 字符**，大 config dump 把前面短 grep 结果挤出预算；`sanitizeOutput(out,200)` 的行数上限也管不到段。
   辅因：压缩走 `renderTranscript`（单条超 1600 字符只留头 60%+尾 40%），8000 字符观察在压缩输入里只剩 1600 → 关键事实落进被省略的中间段；`executedLog` 的 `digestOutput` 同样是**命令级**摘要，仍分不清段。249s 压缩 vs 98.7s 干活说明已在压缩螺旋里。

另记：`store/agent.ts` line 1074-1075 注释写「族计数…写命令执行后清空」，但实现（line 771-772）已改成「写 segment 不再清空全族」——注释与代码相反，后续排查别被误导。

## Agent 第二处只读诊断：截断 → 误判「未按协议」强制结束（2026-09-21，未修）

用户第二张截图：5 步后弹「[任务未完成] 模型连续 3 轮未按协议给出命令或结论」，
最后一轮输出显示为 `<<<`。先用探针（`dist-test/probe-truncate.ts`）逐条验，结论：

- `parseAgentReply("<<<")` / `"<<<RU"` / `"<<<RUN"` → **`done=true, noMarkerFallback=true`**。
  原因：兜底 1（`src/services/agent.ts:857-864`）只 `indexOf(AGENT_RUN_START)`，即必须出现完整的
  11 字符 `<<<RUN>>>`；被截断的标记前缀落不到兜底 1 → 落到兜底 2（line 867）当成「裸文本结论」。
- `store/agent.ts:868-878` 于是 `noMarkerStreak += 1`，3 轮强制结束。而 `truncated`（store:783/807/838）
  **只用来插一条「你被截断了，请精简重发」的用户消息，完全不参与该判定** → 明明是截断，报的却是
  「未按协议」，文案把人带偏。
- **截断只在「正文完全为空」时才走扩容自愈**：`ai.ts` 非流式 line 307 `if (!content.trim())`、
  流式 line 379 `if (!full && emitted === 0)`。正文只剩 `<<<` 这种残片被当**成功**返回 →
  `OutputBudgetError` 不触发 → requestChat 里的「maxTokens×4 且 ≥8192 + 关思考」重试永不发生 →
  **maxTokens 永远停在 4096（`max(aiConfig.maxTokens||2048, 4096)`），每轮都在同预算上被同样截断**。
- **探针还证实一个更危险的点**：`"<<<RUN>>>\nrm -rf /var/lo"`（有 RUN 无 END）→ 兜底 1 抽出
  `commands=["rm -rf /var/lo"]` 原样返回；`store/agent.ts:900` 之后**直接进 reviewCommand／执行，
  没有 `truncated` 门槛**。即截断发生在命令中途时，**写了一半的命令会被真实下发**
  （实测 `... | grep -E 'ssl_prot`）。
- `thinkingDisableExtra` 匹配面：`/\bqwen3(\.\d+)?\b/i` → `Qwen3.5-4B` 命中（已发 enable_thinking:false），
  但 GLM-4.5 / deepseek-r1 不命中；且网关**静默忽略**未知字段时无兜底（只有 400/422 才回退 extraBody）。

修法方向（未实施）：① 截断回复不计入 `noMarkerStreak`，改走独立「连续截断」计数并**升级 maxTokens**；
② 兜底 1 增加「标记前缀」识别（`/<<<R?U?N?>?$/`）或对 `truncated` 直接拒绝下发；
③ 建议顺序是先 ① 再 ②。
