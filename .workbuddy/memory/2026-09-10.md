## 修复：执行超时（23.8s 误判）+ 复杂任务空响应（dl-20260910c→d）

**触发**：用户截图反馈 step 4 `rm` 报「输出超时 23.8s」，复杂任务报「模型未返回任何内容」红色 toast。

**根因1 — 基础超时把硬上限架空（bug）**
- `execCommand` 有两个超时：基础 `timeoutMs`（自适应熔断起点）+ `maxTimeoutMs`（硬上限）。
- 自适应熔断：超过基础超时后 `idle 3s` 判超时（`elapsed >= timeoutMs && now-lastDataAt >= 3000`）。
- 此前：`commandTimeoutMs` 默认 **20000ms**（20s），`commandMaxTimeoutMs` **300000ms**（5min），**UI 只暴露后者**。
- 结果：基础超时 20s 就触发 3s-idle 熔断 → 23s 误判，5min 硬上限永远到不了。用户设的「5分钟」完全失效。
- 修法：① 默认值改为 300000（一致）；② `setCommandMaxTimeoutMs` 同步基础超时；③ **`run()` 里 `const timeoutMs = maxTimeoutMs` 强制覆盖**——绕开 zustand persist 从旧 localStorage 把 20000 重新注回来的坑（默认改了也救不了持久化态）。run() 兜底才是真正的保证。

**根因2 — 空响应一刀切**
- 上一轮加固 ai.ts：content 为空抛 Error → store 首轮停。配错模型（OCR）确实该立即停，但**弱模型复杂任务瞬瞬时空响应**也会触发，浪费一次续跑机会。
- 修法：`run()` 里 chatCompletionRaw 遇「模型未返回任何内容」时**重试 1 次**（同 messages），仍空才抛上去。配错模型两次空 → 原报错生效。

**第一次打包（dl-20260910c）有 bug**：
- Edit 报成功但 `commandTimeoutMs:20000` 没改成 300000（trust-but-verify 失败）—— bundle 里仍是 `2e4`，只 setter 改了。重新 Edit 修了。
- 验证方法：grep asar `commandTimeoutMs:[0-9]*e*[0-9]*` 看真实值（**minified 后 300000→3e5**，20000→2e4，ASCII 数字串，绕过 esbuild 中文转义问题）。

**release 目录锁坑**：dl-20260910c 里的 app.asar 被 Defender/iNodeSec 锁住（和之前 18 个 release 目录同源），`rm -rf` 删除失败（error 32）。safe-delete shim 的 50 文件/轮阈值也拦。**新建目录 dl-20260910d 绕开**（不需 rm）。release 现在的状态：18 个旧目录 + dl-20260910a/b/c(锁/旧) + dl-20260910d(新修复) 都在，重启后能清。

## 11:30 装 Prometheus 跑到 14 步、12 分钟被总超时掐掉 —— 真凶是 `cat` 二进制

**现场**：step 14 = `ls -la /usr/local/bin/prometheus && cat /usr/local/bin/prometheus`，

12 分钟额度被这两步吃干净 → `TASK_TIMEOUT_MS` 触发，「任务执行超时（12 分钟）」。

**三处修复**：
1. **解析期拦「dump 二进制」**（`services/safety.ts` 新增 `isBinaryDumpCommand`，store 里过滤 + 提示）：
   `DUMP_BIN_RE`（cat/tac/strings/xxd/od/hexdump/base64/nl，命令词位置）
   **AND** `BINARY_PATH_RE`（/usr/(local/)?{bin,sbin,lib}/、/{bin,sbin,lib}/、/dev/、/proc/{kcore,self/mem,<pid>/mem}、
   .so/.bin/.o/.a/.exe/.dll/.pyc/.ko/.pem/.key/.p12/.pfx/.jks）。
   **刻意不包 /proc 和 /sys 整体，且放行 /dev/null** —— `cat /proc/cpuinfo`、`cat /dev/null > f` 是高频合法操作，
   一刀切会把正常流程也堵死。这条教训值得记：**"危险路径"清单要按「会不会炸」而不是「像不像系统路径」来列**。
2. **输出洪水兜底**（`services/agent.ts` execCommand）：buffer > 600k 字符即判洪水 →
   **丢弃后续数据 + 立即 break 等待循环 + abortRemoteCommand 打断远端**，buffer/display 只保留头尾。
   这是防任何刷屏（死循环、无 head 的 journalctl）的地板，不只防 cat。
   `ExecResult.flooded` 一路透传到 store，批量/单条两条路径都会给模型补一条"输出过大已截断并中断，别再发同类命令"。
3. **任务总超时可调**：`taskTimeoutMs` 默认 12min → **20min**，UI 选项条加「任务超时」下拉（10/20/30/60 分），
   超时文案带上分钟数并提示可调大。

## 追加：诊断「Agent 接管重复执行命令」的根因（仅讨论，未改码）

用户实测反馈：接管时某些命令被反复执行多次。读码定位到「去重闸门」有 6 个缺口（按严重度排序）：

1. **硬闸门只查批量里的第 1 条**（`src/store/agent.ts:834` `execStats.get(normalizeCmd(commandsToRun[0]))`）。
   批量探测（canBatch）一次跑 2~4 条，第 2~4 条**从不进去重检查**，也从不产生拒绝消息。
2. **`normalizeCmd` 只做空白归一**（`agent.ts:489` `cmd.trim().replace(/\s+/g," ")`）。
   加 `sudo` / `2>&1` / 换参数（`df -h` vs `df -h /`）/ 加 `| head` 都算「新命令」。
   更要命的是提示词规则 3 明确要求「长输出一律自带 `| head -N`」——**等于在教模型主动改写成不同文本**，
   与文本去重天然对立。
3. **`execStats` 是 run() 内的局部常量**（`agent.ts:488`），每次点「开始接管」都从空 Map 重建。
   stop / 超时 / 20 步上限后续跑 → 硬闸门全部失效，只剩 `executedLog` 软提示，
   而软提示只保留最近 30 条（`syncExecLog` 的 `slice(-30)`），长任务早期命令会滑出窗口。
4. **观察被压到 3000 字符**（`OBSERVATION_MAX_CHARS`）+ `focusOutput` 只留「错误行 30 条 + 尾部 40 行」。
   模型没拿到它要的字段 → 换个写法再问一遍。属于「主动重跑」，最隐蔽。
5. **失败命令永不进闸门**：闸门条件是 `dupStat.n >= 2 && dupStat.lastOk`，
   永久失败的命令（如探测不存在的服务）可无限重试，只靠 20 分钟任务总超时兜底。
6. **混写命令的批只跑第 1 条**：模型会把「只读探测 + 安装」混一批提交，系统只执行第 1 条并告知，
   模型下轮再发剩余部分 → 视觉上就是"这条命令跑了好几次"。
   另外被闸门拒绝的轮次 `continue` 时**不建 step、不耗步数预算**，空转可持续到 20 分钟。

补充：闸门设计上允许执行 1~2 次（`n>=2` 才拦），即原本就保证「每条至少能跑 2 遍」。

### 收紧闸门的前提条件（用户追问「会不会影响后续命令执行」）——动闸门必须同时做这 4 件事

1. **剔除重复项，而不是整轮拒绝**。现在 `commandsToRun[0]` 命中即整轮 `continue`；
   如果简单地把检查扩展到「批量里任意一条」，一条重复会拖累同批另外 3 条合法命令。
   正确做法：filter 掉命中的那条，执行剩下的；全被过滤才拒绝并 `continue`（且不耗步数预算）。
2. **成功的写操作（risk ≥ medium）之后清零只读命令计数**。这条是硬需求，不是优化：
   提示词规则 4 要求「装完用 `command -v 包名` / `systemctl status 服务名` 验证」，
   `systemctl status x` 在「装→启→查→改配置→再查」里第 3 次就会被拦。
   主机状态变了，旧结论作废，重查是正当的而不是重复。
3. **`isFresh` 时一并清空持久化的 execStats**。否则「换个新目标」会带着上一任务的命令计数起步，
   新目标需要的探测直接被拒。（agent store 无 persist，加 bucket 字段无需迁移。）
4. **`parsed.thought` 里说明复查理由 → 放行一次**。提示词规则 7 原文承诺了
   「除非明确需要复查同一项（须在思考里说明理由）」，但代码从未实现这个例外 ——
   **现状是提示词承诺、代码不认**。收紧闸门时必须把这个泄压阀补上，否则是在放大已有的不一致。
5. 归一化只剥「无信息量的修饰」（`sudo` / `2>&1` / `| head -N` / `cd X &&` / 行尾 `;`），
   **不要剥参数** —— `df -h` 与 `df -h /` 输出范围不同，不应合并。

不受影响：风险确认（过滤在确认之前）、交互式/二进制拦截、被拒轮次不耗步数预算的既有行为。

### ⚠️ 对上一条「收紧闸门」方案的自我否定（用户否决后重新推导）

用户直接否掉了「加闸门 + 泄压阀」这条路，复盘后同意，理由：

1. **方向错了**：模型重跑 `systemctl status x` 的原因是**忘了结果**，不是忘了「跑过」。
   `executedLog` 钉的是**命令字符串清单**，恰好答非所问 —— 它对模型已知的信息做去重，
   对模型真正缺的信息（输出内容）毫无帮助。
2. **我在提的方案自身可被轻易绕过**（上一轮没想清楚）：
   「thought 里说明复查理由就放行」→ 模型每次写一句"需要复查"就能永久绕过；
   「写操作成功后清零计数」→ 模型跑一条无害的 `mkdir -p /tmp/x`（medium）即可清零全部计数再刷一遍。
   需要配泄压阀的闸门，说明闸门本身不成立。
3. **文本等价性不可判定**：`df -h` / `df -h /` / `df -H` / `df -h --output=...`，
   归一化永远处在「太松没用」和「太紧误伤」之间，打地鼠没有终点。
4. **拒绝比放行更贵**：拒绝要走一整轮 API 往返让模型重规划，而一条只读探测的执行成本极低。
   拦下来省的钱可能不如它多烧的钱。
5. **run() 循环里已经堆了 7+ 道闸门**（空转 / 交互式 / 二进制 / 重复 / 无标记 streak /
   空转 streak / 步数 / 任务超时），每加一道就要配一个泄压阀 —— 这是架构信号，不是参数问题。

**改后的方向（待与用户确认）**：
- **核心**：把「已执行命令清单」升级为**「命令 → 结果摘要」台账**（例如
  `✓ systemctl status prometheus → active (running)`）。改的是 `executedLog.push` 附近约 5 行，
  零阻塞、零误伤，直接消除重跑动机。
- **次要**：把「拒绝重复」换成「命中缓存直接回填旧结果」，不产生拒绝往返；
  缓存随成功的写操作失效。
- **保留**：交互式 / 二进制 dump 拦截（属正确性与安全，不是优化），但重复闸门可考虑整段删除。
- 注意 `OBSERVATION_MAX_CHARS = 3000` + `focusOutput` 丢非错误行，也是「模型看不到要点而重跑」的元凶之一。

### 追加：Agent 任务耗时的结构分析与优化杠杆（仅分析，未改码）

一轮耗时的构成（**按代码结构推导的估算，非实测**）：网络往返 + prefill + 生成 + 命令执行 + 压缩。
其中两个非显而易见的大头：

1. **前缀缓存被自己破坏**（零功能改动、纯收益）：
   `syncExecLog()` 每轮把「已执行命令清单」`splice` 进 `messages[1]` 或 `[2]`（`src/store/agent.ts:506-513`），
   而这条消息**每轮内容都变**。它位于前缀中段 → 它之后上万 token 的历史观察每轮全部 cache-miss。
   修法：把每轮变化的消息（exec log、新观察）一律**追加到数组末尾**，让
   `[system][goal/plan][历史...]` 保持逐字节稳定的前缀，命中 DeepSeek/OpenAI/Anthropic 的自动前缀缓存。
   ⚠️ 张力：`hardTrim`/`assembleCompressedMessages` 会**重写整个数组** → 压缩一触发前缀缓存就全废。
   所以「压缩降频」和「缓存友好」是同一个方向。

2. **上下文压缩卡在主链路上**：`await maybeCompress()`（`agent.ts:614`）每轮开头执行，
   压缩本身是**一次完整的额外 LLM 调用**（输入 = 中间段 transcript 上万字符，输出 = 摘要）。
   20 步任务触发 5~8 次 = 5~8 次额外往返。优化：提高阈值
   （现为 `COMPRESS_TRIGGER=12` / `MAX_CONTEXT_TOKENS=24000`）、用更小更快的模型专门做压缩、
   或把压缩挪出关键路径。

其他杠杆（按性价比）：
- **先加度量**：现在完全无 token/耗时统计，无法定位。加「每轮 prompt tokens / completion tokens / 耗时」。
- **减少轮数**：只读批量上限 4 → 6~8；杜绝空转/重复轮（每轮固定成本 = RTT + 整个 system prompt 的 prefill）。
- **UI 回推争用主线程**：`onOutput` 每 200ms → `updateStepItem` → zustand set → React 重渲染，
  且 `capOutput` 每次对**累积全量文本**做 `sanitizeOutput`（正则+split+逐行），输出越长越慢；
   这些都在 renderer 主线程，与 Agent 循环**同线程**。改：节流到 500ms + 只对增量 sanitize。
- **AGENT_SYSTEM_PROMPT 瘦身**：每轮全量重发（≈2600 中文字），规则越堆越多。
  有前缀缓存后收益打折，优先级低于第 1 条。
- 固定 sleep（`sleep(sawEnd ? 80 : 150)` + 60ms 轮询）每命令约 150~250ms，小头。

### 追加：上述三条优化的利弊与「未验证前提」（重要，别当成免费提速）

**第 2 条「前缀缓存友好化」有两个硬前提，未验证前不该动手**：
- 缓存要真的生效。用户如果走**中转/聚合网关**，前缀缓存可能根本不启用；Anthropic 还需显式 `cache_control`。
- `hardTrim`/压缩会**重写整个消息数组** → 触发一次缓存就全废。若 trim 每 1~2 轮就触发，
  改消息顺序承担了行为变化风险却拿不到收益，收益/风险比不成正比。
- 行为变化风险：exec log / plan 从「system 之后」挪到「最末尾」会改变注意力分布
  （lost-in-the-middle 效应下末尾未必更差，但**方向无法预判，只能实测**）。

**第 3 条「压缩降频」有反作用**：
- 上下文变长的代价是**每轮 prefill 都变贵**，省的是「每 6 轮一次压缩」。
  轮数多时可能**净变慢**，不是免费。
- **硬风险**：阈值提到 40k 会撞模型上下文窗口。若用户用小模型（如记忆里出现过的 Qwen3.5-4B），
  窗口可能只有 32k → 直接请求失败，表现为「AI 不回复」。**降频前必须知道模型窗口大小**，代码里没有这个信息。

**第 1 条「加度量」有兼容性风险**：
- 流式响应**默认不返回 usage**，需要显式加 `stream_options: { include_usage: true }` 顶层字段。
  已有的 `droppedExtraBody` 兜底只覆盖 `config.extraBody`（`src/services/ai.ts:406`），
  **新增顶层字段不在兜底范围内**，某些网关会直接 400 把 Agent 搞挂。踩过同类坑（enable_thinking）。

**优先级需要修正**：上面三条都在优化「单轮成本」；而**减少轮数是乘数级杠杆**
（20 轮 → 10 轮 = 砍半，单轮提速 30% 只是 ×0.7）。重复执行/批量上限属于后者，应排更前。

**战略观察**：run() 已堆 7+ 道闸门（每加一道要配泄压阀），现在又要叠性能优化层。
「让模型少犯错的规则」与「让循环更快的规则」是两套互相干扰的补丁，可能需要重构 run()。

### 追加：定稿方案「零回归提速」（用户要求：不影响 AI 效果 + 提升效率）

**原则：只做「信息不减、语义不变」的改动。** 凡是会改变模型输入语义或引入反作用的，一律排除。

**第 1 层 —— 纯本地开销（完全不碰模型输入输出）**
- `capOutput` 每次对**累积全量文本**做 `sanitizeOutput` → 改增量 sanitize（照抄 `execCommand` 内部 `display` 的增量模式）。
- `onOutput` 每 200ms → zustand set → React 重渲染，与 Agent 循环**同线程**争用；节流到 500ms。
- `execCommand` 轮询 60ms → 25ms：纯感知延迟，哨兵判定逻辑不变，零正确性风险。

**第 2 层 —— 上下文「信息只增不减」的等价重写（乘数级：减少重跑轮次）**
- `executedLog` 从「命令清单」升级为「命令 → **输出原文片段**」台账。
  ⚠️ 必须是**原文截录**（如首行 + ≤60 字符），**不能让模型生成概括**（会产生误导性幻觉）。
  窗口限最近 ~8 条，使总字符数与现状（30 条纯命令 ≈900 字符）基本持平 ——
  **同样 token 预算换成更高信息密度**，不是新增负担。
- `focusOutput` 改为保留「首 20 行 + 错误行 + 尾 40 行」。现状是「有错误关键词就**只**留错误行+尾部」，
  把中间的正常信息全丢 → 模型缺信息 → 重跑。
- pin 消息（PLAN_PIN / EXEC_LOG）的说明文字精炼：信息等价、措辞缩短，每轮省 token。

**第 3 层 —— 度量（可选，带自我保护）**
- 每轮记录 prompt/completion tokens 与耗时。`stream_options` 顶层字段必须走「被拒即摘掉并永久禁用」，
  否则严格网关 400 会把 Agent 搞挂（现有 `droppedExtraBody` 只覆盖 `extraBody`，需扩展）。

**明确不做（及原因）**：
- 前缀缓存友好化 —— 网关是否支持未验证 + 消息顺序变化有行为风险 + trim 会破坏前缀。
- 压缩降频 —— 每轮 prefill 变贵，可能净变慢；阈值过高会撞小模型上下文窗口致请求失败。
- 只读批量上限 4 → 8 —— 批量串行，单批最坏耗时 8×5min = 40min > 任务总时限 20min。
- system prompt 大改 —— 改变模型输入语义。

### 追加：截图实锤的「盲目试错探测」缺陷（curl 猜路径）

用户截图（步骤 6~10，目标疑似「装 Prometheus 后验证状态」）：

```
6  curl -s http://localhost:9090/-/health        | head -50   只读 执行完成 0.2s
7  curl -s http://localhost:9090/metrics         | head -50   只读 执行完成 0.1s
8  curl -s http://localhost:9090/-/status        | head -100  只读 执行完成 0.2s
9  curl -s http://localhost:9090/api/v1/status   | head -100  只读 执行完成 0.1s
10 curl -s http://localhost:9090/-/health        | head -50   只读 执行完成 0.2s   ← 与步骤 6 逐字相同
```

**判定：4/5 条路径是错的。** Prometheus 真实端点：`/-/healthy`（不是 `/-/health`）、`/-/ready`、
`/metrics`（唯一命中的）、`/api/v1/status/{config,runtimeinfo,flags}`（不是裸 `/api/v1/status`）。
`/-/status` 根本不存在。除步骤 7 外全是 404。

**暴露的四个缺陷**：
1. **盲目试错取代了服务发现**：全程没有一步确认 9090 端口有没有在监听。
   零成本正确做法：`ss -lntp | grep -w 9090`。端口没监听就根本不该 curl。
2. **看到 4 次 404 仍不换策略**：`curl -s` 对 HTTP 404 **仍会打印响应体**（它只静默进度条和连接错误），
   所以模型是**看见了** "404 page not found" 还继续换字符串。规则 8「同一根因最多换 2~3 种方式」
   在代码里没有实现，且模型把「换个 URL 路径」当成了「换方式」。
3. **重复执行实锤**：步骤 6 与 10 逐字相同，间隔 3 步。`execStats` 是 `n>=2` 才拦 → 第二次必然放行。
4. **UI 徽章误导**：`AgentPanel.tsx:383-385` 仅在 `exitCode !== null && exitCode !== 0` 时显示失败，
   而 curl 收到 404 时退出码是 **0** → 绿色「执行完成」。5 条里 4 条 404 却全部显示成功。
   文案「执行完成」暗示成功，建议改中性词（如「已执行」）。

**注意**：这是**效果**问题不是效率问题 —— 5 步单条探测 = 5 次完整 AI 往返，
且其中 4 步是无用功。正好实证了「轮数是乘数级杠杆」。

**根因**：提示词里**没有「HTTP / 服务类诊断规范」**。规则 4 只讲安装部署，规则 5 只讲长耗时任务，
没有任何一条要求「先确认端口监听，再确认端点，禁止猜路径，失败要升级到进程/日志/配置层面」。

**修复方向**：先改提示词（加服务诊断规范 + 失败升级要求 + `curl` 用 `-sS` 禁止裸 `-s`）；
引擎侧可考虑在 observation 里**告知**「这是第 N 次对同一端点的失败探测」（提供信息而非拦截，符合既定原则）。

1. **只检查 `commandsToRun[0]`** —— 批量里的第 2~4 条从来没被检查过，而批量只读探测
   恰是最主要执行路径。
2. **命中就整轮 `continue`** —— `[新命令A, 重复命令, 新命令B]` 会拿 A、B 陪葬。
   改为**只剔除重复那条**，其余照常执行；全被剔除才拒绝本轮。
3. **按整行计数** —— `systemctl restart x && systemctl status x` 与单独的
   `systemctl status x` 是两个键，于是**把查询包进别的命令里就能绕开去重**。
   这正是截图那条的成因：第 9 步的 status 没被记，第 10 步只数到 1 次 → 放行。

修法：新增 `splitSubCommands()`（只拆顶层 `&&`/`;`，引号内不拆、`|` 不拆、
单 `&` 不拆因为 `2>&1` 含 `&`）+ `createDupTracker()`（record/isDuplicate/lastDigest），
两者都放在 `services/agent.ts`（纯函数、可单测），store 只调用。
单条命令只算自己一个键（拆开只会得到自身，避免重复计数）。
子命令**全部**达标才算重复：只要有一条是新的，整条照常执行。

**拒绝时回填输出片段**（`lastDigest`）：不是干巴巴拒绝，把「上次拿到的结果」一并给模型，
这样它不必为了「再看一眼」多花一轮往返。台账条目现在存 `{n, lastOk, digest}`。

**`dupStreak` 兜底**：重复命令被剔除后 `n` 不会增长（没真的执行），所以单靠台账无法收敛 ——
模型可以一直重发同一条、一直被拒，每轮都是一次完整 API 往返。连拒 3 轮强制收尾
（与 `lowValueStreak` 同一思路，但独立计数，因为被拒轮不建 step、不耗步数预算）。

**保留 `n >= 2` 阈值不变**：给「装完 / 启动后复查状态」留余量。**没做「写操作后清零读计数」**

按 riskLevel 认不出来），且泄压阀本身可被绕过（跑一条无害 medium 命令即可清空）。留作遗留项。

## 单行 `;` 串命令的退出码语义（2026-09-10 下午 3，只分析未改码）

**用户截图**：nfs-server 任务第 7 步，**单行 10 条子命令**：
`rm -rf …/rpc_pipefs/gssd/clntXX; rm -rf …/gssd; rm -rf …/rpc_pipefs; rm -rf /var/lib/nfs;`
`rm -rf /var/log/nfs*; rm -rf /var/run/nfs*; rm -rf /var/tmp/nfs*;`
`ls -la /var/lib/nfs/ 2>/dev/null; ls -la /var/log/nfs* 2>/dev/null; ls -la /var/run/nfs* 2>/dev/null`
UI：高风险 / **执行失败** / 0.2s。用户问「是不是一次命令太多导致失败」。**结论：不是条数问题。**

### 直接成因：`$?` 只反映 `;` 串的最后一条
包装脚本（`services/agent.ts:391`）：
`echo "BEGIN"; <用户命令> 2>&1; echo "EXIT:$?"; echo "END"`
`;` **不是** `&&` → 不 fail-fast，且 `$?` = 整串**最后一条**的退出码。
末条 = `ls -la /var/run/nfs*` → bash 默认 glob 不匹配时把字面量传给 ls → `ls: cannot access`
→ 退出码 **2** → `isOk()`（`store/agent.ts:180`：`!error && (exitCode===0||exitCode===null)`）为 false
→ `step.status="failed"` → UI「执行失败」。**前 7 条 `rm` 的成败根本没有进入判定。**

### 证据（非推测）：UI 文案本身证明了「命令真的跑了」
`AgentPanel.tsx:404-409`：`step.status==="failed"` 时显示 `items.find(it=>it.error)?.error ?? "执行失败"`。
- 异常路径（`store/agent.ts:1132-1137` catch）会写 `error` → 文案会变成错误消息；
- 单条正常路径（`:1146-1152`）`error: res.error` 而 `ExecResult.error` 只在批量路径（`services/agent.ts:563`）被赋值。
所以截图显示裸「执行失败」= 走的是单条路径且 **exitCode ≠ 0**。0.2s 也符合「命令真跑了」。
→ 排除「终端断开 / 下发失败」（那两条会带文案）。

### 为什么「条数」不是原因，但有三个口径问题
| 环节 | 计数口径 | 这条命令的结果 |
|---|---|---|
| 单轮条数上限 `MAX_BATCH_COMMANDS=4` | 按**行**（`splitCommandBlock` 只按 `\n` 拆） | 10 条子命令 = **1 条**，上限完全不生效 |
| 风险确认 `reviewCommand` | 按整行 | **一次点击放行 7 条 `rm -rf`** |
| 去重台账 `createDupTracker` | 按**子命令**（`splitSubCommands` 拆 `;`/`&&`） | 10 个独立键 —— 唯一口径正确的地方 |

即：`parseAgentReply` → `splitCommandBlock`（`:43`，仅按换行）→ 单行 = 1 条 → `canBatch=false`
→ 走单条「写命令」路径。**条数上限与确认粒度都只按行，模型可以用 `;` 无上限打包。**

### 顺带发现（引擎侧，未改）
包装脚本把 ` 2>&1` **追加在用户命令末尾**，而 shell 重定向**从左到右**生效：
末条 `ls … 2>/dev/null 2>&1` → `2>/dev/null` 先设 fd2=/dev/null，再被 `2>&1` 覆盖回 PTY。
**用户自己的 `2>/dev/null` 被抵消**，错误文本反而会漏进输出（好处：可用于印证上面的诊断）。
中间几条（非末条）没有追加 `2>&1`，抑制仍生效。

### 命令本身的语义问题（与数量无关）
- 4 层嵌套删除（`…/gssd/clntXX` → `…/gssd` → `…/rpc_pipefs` → `/var/lib/nfs`）互相包含，纯冗余。
- `rm -rf /var/lib/nfs` 删的是 **NFS 状态目录**（statd/lockd 的 sm/statd 数据），不是标准排障动作；
  且 `…/rpc_pipefs` 是**挂载点**，运行时删不掉（`Device or resource busy`），`-f` 让其静默失败。
- 删完 `/var/lib/nfs` **立刻 `ls` 去检查它** → 该检查注定失败。
- 三个 `ls` 用退出码表达「找没找到」，却被引擎当成「命令成败」。

### 用户自检方法
展开第 7 步输出；若出现 `ls: cannot access '/var/run/nfs*': No such file or directory` 即印证。

## 实证补正：第 9 步那 13 条 rm 是**真失败**，不是被末条退出码冤枉（2026-09-10 下午 4，仍只分析未改码）

用户补了两张图：第 9 步命令（13 条 `rm -rf` + 2 条 `ls`，高风险/执行失败/0.2s）
+ 终端实际输出（满屏 `rm: cannot remove '…': Operation not permitted`）。

**上一轮推测被推翻一半**：我说「rm 大概率都成功，是末条 `ls` 把整步判失败」。
实际 rm **全部真失败**。退出码机制的分析仍成立，但「失败原因」要改。

### 真因：`/var/lib/nfs/rpc_pipefs` 是**挂载点**，不是普通目录
- `rpc_pipefs` 是**内核伪文件系统**（NFS 客户端与 rpc.gssd / rpc.idmapd / rpc.statd
  通信用的命名管道）。条目（`gssd/ nfsd/ cache/ statd/ portmap/ mount/ lockd/ nfs/
  nfsd4_cb/` 及 `gssd/clntXX/{gssd,info}`）由**内核创建**，该 fs 未实现 unlink/rmdir
  → 任何删除一律返回 **EPERM** → `Operation not permitted`。
- **截图自带证据，无需推测**：所有条目 `drwxrwxrwx` + **size 0** + 时间戳全同
  （`Sep 10 09:25`）+ 父目录 `total 0`。真实磁盘目录不可能长这样 —— 虚拟 fs 签名。
- **正确路径**：`mount | grep -E 'rpc_pipefs|nfsd'` 确认 → `umount /var/lib/nfs/rpc_pipefs`
  → `systemctl restart nfs-server`（服务重建）。是**卸载**，不是删文件。

### 为什么 13 条 rm 刷出约 20 条错误
`rm -rf` 递归。除了 12 条针对子目录的 rm，第 12 条 `rm -rf /var/lib/nfs/rpc_pipefs`
会把整个子树**再走一遍** → 同一批名字第二次出现（截图第二段重复的
`gssd/clntXX/gssd`、`nfsd`、`cache`、`nfsd4_cb`、`statd`、`portmap`、`nfs`）。
**这条命令里有 12 条 rm 在重复做对方已经做过的事。**

### 界面判定（机制没变，但这次是「碰巧判对」）
`执行失败` = 末条 `ls -la /var/log/nfs*` 的退出码（glob 不匹配 → `ls: cannot access` → exit 2）。
13 条 rm 的失败**没参与**判定。**危险的是反例**：若末条 ls 恰好 exit 0，
界面会显示绿色「已执行」，而 13 条 rm 全在报错。这才是真正的 bug。

### 模型策略问题（本次最值得记）
同一条思路的**第二次迭代**：上张截图是第 ⑦ 步，这张是第 ⑨ 步，把子目录**列得更全**了。
它把「换更细的路径 / 列更全」当成「换了一种方式」，实际一次方法都没换。
而且 `ls` 的输出（`drwxrwxrwx … total 0`）**就在它自己刚拿到的结果里 —— 它没读**。

### 代码侧的印证（都是已记录的缺口）
1. 单行 `;` 串只取末条退出码 → 信息不足（见 MEMORY.md 同条）。
2. **提示词没有任何一条讲「目标可能是挂载点」** —— `mount` / `umount` 这两个
   关键词在 AGENT_SYSTEM_PROMPT 里完全缺失。这是可补的高价值规则。

## 单行 `;` 串治理：一行内重复 46 次子命令（2026-09-10 下午 6，已改码 + 打包）

**用户截图**：目标「把nsf卸载干净」，终端被刷成一面墙 —— 同一条
`rpm -qf /etc/cron.d/nsf 2>/dev/null` 逐字重复约 46 次，用 `;` 串成**一行**。
UI：接管中 / 2 步 / AI 2.6s / 5.5k tok。另一张图显示输出里有
`/var/lib/docker/overlay2/...` 一堆路径 + `rpm: no arguments given for query`
+ `Unit nsf.service could not be found.` + `No var/lib/nsf dir`。

### 根因（确定性，不是「模型乱发」）

**「一行内子命令没有条数上限」这条结构缺口被触发了。** 链路：
`parseAgentReply` → `splitCommandBlock`（**只按 `\n` 拆**）→ 一行内 46 个子命令
= **1 条命令** → `canBatch=false`（length===1）→ `sliced=[allCandidates[0]]`
→ **条数上限、风险确认粒度、跨轮去重台账全部看不见它**。

三条口径对照（这次实证补上了第二条）：
| 环节 | 口径 | 这一行的结果 |
|---|---|---|
| 单轮条数上限 `AGENT_MAX_BATCH_COMMANDS=4` | 按行 | 10/46 条子命令 = 1 条，上限不生效 |
| 跨轮去重 `createDupTracker` | 按子命令 | 首次下发时计数全 0，行内重复不可见 |
| 命令行长度 | **无任何限制** | 一条 ~1700 字符的单行原样下发 |

**为什么"一行"是关键判据**：若模型输出的是 46 行，`MAX_BATCH_COMMANDS` 会截到 4 条，
终端不可能出现 46 次重复。所以必然是**一行内含 46 个子命令** —— 提示词规则 2 本来就
要求「每行一条」，模型违反了协议，而引擎对违反没有兜底。

**附带风险（未实测，标注为推测）**：Linux PTY 规范模式下行缓冲有限（≤4096），
整行超长会被内核截断，而包装脚本把 `; echo "TERMAI_EXIT_x:$?"; echo "TERMAI_END_x"`
放在**末尾** → 截断=丢哨兵 → 命令跑完了引擎却等不到结束，只能耗到 20s/60s 超时。
这能解释「一直在不断」的观感，但**没在 PTY 上实测**。

### 目标串的笔误是诱因

目标是 `nsf`，而系统里存在的是 `nfs`（此前几轮全是 NFS：rpc_pipefs / /var/lib/nfs）。
模型查到 `nsf.service` / `/var/lib/nsf` 都不存在后：① 转去做**全盘搜索**
（`grep -r nsf /` 扫进 docker overlay2，就是第二张图那堆路径）；② 抓 `/etc/cron.d/nsf`
这种无关文件反复 `rpm -qf`；③ 输出退化成重复。**提示词里没有任何一条讲
「目标名查不到时先怀疑拼写」或「禁止全盘搜索」** —— 这是可补的规则。

### 改动

1. **`services/agent.ts` 新增 `splitCommandParts`**（带分隔符的分词）+ 把
   `splitSubCommands` 改为委托它（去重计数语义不变，零回归）。
   保留 `;` / `&&` 的原因是**要按原样拼回去** —— 一律重拼成 `;` 会丢掉 fail-fast 语义。
2. **新增 `sanitizeCommandLine(cmd)`**：
   - 折叠**逐字相同**的子命令（比较前把连续空白压成一个空格）；
   - 剩余子命令 > `AGENT_MAX_SUB_COMMANDS_PER_LINE`(8) 或整行 > 2000 字符 → **整条拒绝**
     （overflow 非空），**不静默截断** —— 截断会让模型以为命令跑完了；
   - **无折叠则原样返回**（连空格都不动），让净化在无必要时零副作用。

## 2026-09-11 修复：多行循环被压平成非法 bash（"执行的什么东西，啥都不是"）

- `flattenCommand`：丢弃纯注释行；行尾处于「等后续内容」状态（`&& || | ; & { (` +

- 新增 `needsScriptFile(command)`：多行且含 结构关键字/注释/heredoc → **落盘成 /tmp 临时脚本**
