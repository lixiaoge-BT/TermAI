## 修复：执行超时（23.8s 误判）+ 复杂任务空响应（dl-20260910c→d）

**触发**：用户截图反馈 step 4 `rm` 报「输出超时 23.8s」，复杂任务报「模型未返回任何内容」红色 toast。

**根因1 — 基础超时把硬上限架空（bug）**
- `execCommand` 有两个超时：基础 `timeoutMs`（自适应熔断起点）+ `maxTimeoutMs`（硬上限）。
- 自适应熔断：超过基础超时后 `idle 3s` 判超时（`elapsed >= timeoutMs && now-lastDataAt >= 3000`）。
- 此前：`commandTimeoutMs` 默认 **20000ms**（20s），`commandMaxTimeoutMs` **300000ms**（5min），**UI 只暴露后者**。
- 结果：基础超时 20s 就触发 3s-idle 熔断 → 23s 误判，5min 硬上限永远到不了。用户设的「5分钟」完全失效。
- 修法：① 默认值改为 300000（一致）；② `setCommandMaxTimeoutMs` 同步基础超时；③ **`run()` 里 `const timeoutMs = maxTimeoutMs` 强制覆盖**——绕开 zustand persist 从旧 localStorage 把 20000 重新注回来的坑（默认改了也救不了持久化态）。run() 兜底才是真正的保证。

**根因2 — 空响应一刀切**
- 上一轮加固 ai.ts：content 为空抛 Error → store 首轮停。配错模型（OCR）确实该立即停，但**弱模型复杂任务瞬瞬时空响应**也会触发，浪费一次续跑机会。
- 修法：`run()` 里 chatCompletionRaw 遇「模型未返回任何内容」时**重试 1 次**（同 messages），仍空才抛上去。配错模型两次空 → 原报错生效。

**第一次打包（dl-20260910c）有 bug**：
- Edit 报成功但 `commandTimeoutMs:20000` 没改成 300000（trust-but-verify 失败）—— bundle 里仍是 `2e4`，只 setter 改了。重新 Edit 修了。
- 验证方法：grep asar `commandTimeoutMs:[0-9]*e*[0-9]*` 看真实值（**minified 后 300000→3e5**，20000→2e4，ASCII 数字串，绕过 esbuild 中文转义问题）。

**release 目录锁坑**：dl-20260910c 里的 app.asar 被 Defender/iNodeSec 锁住（和之前 18 个 release 目录同源），`rm -rf` 删除失败（error 32）。safe-delete shim 的 50 文件/轮阈值也拦。**新建目录 dl-20260910d 绕开**（不需 rm）。release 现在的状态：18 个旧目录 + dl-20260910a/b/c(锁/旧) + dl-20260910d(新修复) 都在，重启后能清。

## 11:30 装 Prometheus 跑到 14 步、12 分钟被总超时掐掉 —— 真凶是 `cat` 二进制

**现场**：step 14 = `ls -la /usr/local/bin/prometheus && cat /usr/local/bin/prometheus`，
标记「执行完成 / 输出超时 320.8s」，终端左半屏被乱码刷满（那 100MB+ 的 ELF）。
step 11 `yum install -y --skip-broken golang-github-prometheus` 也花了 107s。
12 分钟额度被这两步吃干净 → `TASK_TIMEOUT_MS` 触发，「任务执行超时（12 分钟）」。

**三处修复**：
1. **解析期拦「dump 二进制」**（`services/safety.ts` 新增 `isBinaryDumpCommand`，store 里过滤 + 提示）：
   `DUMP_BIN_RE`（cat/tac/strings/xxd/od/hexdump/base64/nl，命令词位置）
   **AND** `BINARY_PATH_RE`（/usr/(local/)?{bin,sbin,lib}/、/{bin,sbin,lib}/、/dev/、/proc/{kcore,self/mem,<pid>/mem}、
   .so/.bin/.o/.a/.exe/.dll/.pyc/.ko/.pem/.key/.p12/.pfx/.jks）。
   **刻意不包 /proc 和 /sys 整体，且放行 /dev/null** —— `cat /proc/cpuinfo`、`cat /dev/null > f` 是高频合法操作，
   一刀切会把正常流程也堵死。这条教训值得记：**"危险路径"清单要按「会不会炸」而不是「像不像系统路径」来列**。
2. **输出洪水兜底**（`services/agent.ts` execCommand）：buffer > 600k 字符即判洪水 →
   **丢弃后续数据 + 立即 break 等待循环 + abortRemoteCommand 打断远端**，buffer/display 只保留头尾。
   这是防任何刷屏（死循环、无 head 的 journalctl）的地板，不只防 cat。
   `ExecResult.flooded` 一路透传到 store，批量/单条两条路径都会给模型补一条"输出过大已截断并中断，别再发同类命令"。
3. **任务总超时可调**：`taskTimeoutMs` 默认 12min → **20min**，UI 选项条加「任务超时」下拉（10/20/30/60 分），
   超时文案带上分钟数并提示可调大。

**测试**：safety.test.ts 加 3 个用例（拦真实闯祸命令 / 其它 dump 形态 / **绝不误伤常规只读探测**——后者是回归保护重点）。

## 追加：诊断「Agent 接管重复执行命令」的根因（仅讨论，未改码）

用户实测反馈：接管时某些命令被反复执行多次。读码定位到「去重闸门」有 6 个缺口（按严重度排序）：

1. **硬闸门只查批量里的第 1 条**（`src/store/agent.ts:834` `execStats.get(normalizeCmd(commandsToRun[0]))`）。
   批量探测（canBatch）一次跑 2~4 条，第 2~4 条**从不进去重检查**，也从不产生拒绝消息。
2. **`normalizeCmd` 只做空白归一**（`agent.ts:489` `cmd.trim().replace(/\s+/g," ")`）。
   加 `sudo` / `2>&1` / 换参数（`df -h` vs `df -h /`）/ 加 `| head` 都算「新命令」。
   更要命的是提示词规则 3 明确要求「长输出一律自带 `| head -N`」——**等于在教模型主动改写成不同文本**，
   与文本去重天然对立。
3. **`execStats` 是 run() 内的局部常量**（`agent.ts:488`），每次点「开始接管」都从空 Map 重建。
   stop / 超时 / 20 步上限后续跑 → 硬闸门全部失效，只剩 `executedLog` 软提示，
   而软提示只保留最近 30 条（`syncExecLog` 的 `slice(-30)`），长任务早期命令会滑出窗口。
4. **观察被压到 3000 字符**（`OBSERVATION_MAX_CHARS`）+ `focusOutput` 只留「错误行 30 条 + 尾部 40 行」。
   模型没拿到它要的字段 → 换个写法再问一遍。属于「主动重跑」，最隐蔽。
5. **失败命令永不进闸门**：闸门条件是 `dupStat.n >= 2 && dupStat.lastOk`，
   永久失败的命令（如探测不存在的服务）可无限重试，只靠 20 分钟任务总超时兜底。
6. **混写命令的批只跑第 1 条**：模型会把「只读探测 + 安装」混一批提交，系统只执行第 1 条并告知，
   模型下轮再发剩余部分 → 视觉上就是"这条命令跑了好几次"。
   另外被闸门拒绝的轮次 `continue` 时**不建 step、不耗步数预算**，空转可持续到 20 分钟。

补充：闸门设计上允许执行 1~2 次（`n>=2` 才拦），即原本就保证「每条至少能跑 2 遍」。

### 收紧闸门的前提条件（用户追问「会不会影响后续命令执行」）——动闸门必须同时做这 4 件事

1. **剔除重复项，而不是整轮拒绝**。现在 `commandsToRun[0]` 命中即整轮 `continue`；
   如果简单地把检查扩展到「批量里任意一条」，一条重复会拖累同批另外 3 条合法命令。
   正确做法：filter 掉命中的那条，执行剩下的；全被过滤才拒绝并 `continue`（且不耗步数预算）。
2. **成功的写操作（risk ≥ medium）之后清零只读命令计数**。这条是硬需求，不是优化：
   提示词规则 4 要求「装完用 `command -v 包名` / `systemctl status 服务名` 验证」，
   `systemctl status x` 在「装→启→查→改配置→再查」里第 3 次就会被拦。
   主机状态变了，旧结论作废，重查是正当的而不是重复。
3. **`isFresh` 时一并清空持久化的 execStats**。否则「换个新目标」会带着上一任务的命令计数起步，
   新目标需要的探测直接被拒。（agent store 无 persist，加 bucket 字段无需迁移。）
4. **`parsed.thought` 里说明复查理由 → 放行一次**。提示词规则 7 原文承诺了
   「除非明确需要复查同一项（须在思考里说明理由）」，但代码从未实现这个例外 ——
   **现状是提示词承诺、代码不认**。收紧闸门时必须把这个泄压阀补上，否则是在放大已有的不一致。
5. 归一化只剥「无信息量的修饰」（`sudo` / `2>&1` / `| head -N` / `cd X &&` / 行尾 `;`），
   **不要剥参数** —— `df -h` 与 `df -h /` 输出范围不同，不应合并。

不受影响：风险确认（过滤在确认之前）、交互式/二进制拦截、被拒轮次不耗步数预算的既有行为。

### ⚠️ 对上一条「收紧闸门」方案的自我否定（用户否决后重新推导）

用户直接否掉了「加闸门 + 泄压阀」这条路，复盘后同意，理由：

1. **方向错了**：模型重跑 `systemctl status x` 的原因是**忘了结果**，不是忘了「跑过」。
   `executedLog` 钉的是**命令字符串清单**，恰好答非所问 —— 它对模型已知的信息做去重，
   对模型真正缺的信息（输出内容）毫无帮助。
2. **我在提的方案自身可被轻易绕过**（上一轮没想清楚）：
   「thought 里说明复查理由就放行」→ 模型每次写一句"需要复查"就能永久绕过；
   「写操作成功后清零计数」→ 模型跑一条无害的 `mkdir -p /tmp/x`（medium）即可清零全部计数再刷一遍。
   需要配泄压阀的闸门，说明闸门本身不成立。
3. **文本等价性不可判定**：`df -h` / `df -h /` / `df -H` / `df -h --output=...`，
   归一化永远处在「太松没用」和「太紧误伤」之间，打地鼠没有终点。
4. **拒绝比放行更贵**：拒绝要走一整轮 API 往返让模型重规划，而一条只读探测的执行成本极低。
   拦下来省的钱可能不如它多烧的钱。
5. **run() 循环里已经堆了 7+ 道闸门**（空转 / 交互式 / 二进制 / 重复 / 无标记 streak /
   空转 streak / 步数 / 任务超时），每加一道就要配一个泄压阀 —— 这是架构信号，不是参数问题。

**改后的方向（待与用户确认）**：
- **核心**：把「已执行命令清单」升级为**「命令 → 结果摘要」台账**（例如
  `✓ systemctl status prometheus → active (running)`）。改的是 `executedLog.push` 附近约 5 行，
  零阻塞、零误伤，直接消除重跑动机。
- **次要**：把「拒绝重复」换成「命中缓存直接回填旧结果」，不产生拒绝往返；
  缓存随成功的写操作失效。
- **保留**：交互式 / 二进制 dump 拦截（属正确性与安全，不是优化），但重复闸门可考虑整段删除。
- 注意 `OBSERVATION_MAX_CHARS = 3000` + `focusOutput` 丢非错误行，也是「模型看不到要点而重跑」的元凶之一。

### 追加：Agent 任务耗时的结构分析与优化杠杆（仅分析，未改码）

一轮耗时的构成（**按代码结构推导的估算，非实测**）：网络往返 + prefill + 生成 + 命令执行 + 压缩。
其中两个非显而易见的大头：

1. **前缀缓存被自己破坏**（零功能改动、纯收益）：
   `syncExecLog()` 每轮把「已执行命令清单」`splice` 进 `messages[1]` 或 `[2]`（`src/store/agent.ts:506-513`），
   而这条消息**每轮内容都变**。它位于前缀中段 → 它之后上万 token 的历史观察每轮全部 cache-miss。
   修法：把每轮变化的消息（exec log、新观察）一律**追加到数组末尾**，让
   `[system][goal/plan][历史...]` 保持逐字节稳定的前缀，命中 DeepSeek/OpenAI/Anthropic 的自动前缀缓存。
   ⚠️ 张力：`hardTrim`/`assembleCompressedMessages` 会**重写整个数组** → 压缩一触发前缀缓存就全废。
   所以「压缩降频」和「缓存友好」是同一个方向。

2. **上下文压缩卡在主链路上**：`await maybeCompress()`（`agent.ts:614`）每轮开头执行，
   压缩本身是**一次完整的额外 LLM 调用**（输入 = 中间段 transcript 上万字符，输出 = 摘要）。
   20 步任务触发 5~8 次 = 5~8 次额外往返。优化：提高阈值
   （现为 `COMPRESS_TRIGGER=12` / `MAX_CONTEXT_TOKENS=24000`）、用更小更快的模型专门做压缩、
   或把压缩挪出关键路径。

其他杠杆（按性价比）：
- **先加度量**：现在完全无 token/耗时统计，无法定位。加「每轮 prompt tokens / completion tokens / 耗时」。
- **减少轮数**：只读批量上限 4 → 6~8；杜绝空转/重复轮（每轮固定成本 = RTT + 整个 system prompt 的 prefill）。
- **UI 回推争用主线程**：`onOutput` 每 200ms → `updateStepItem` → zustand set → React 重渲染，
  且 `capOutput` 每次对**累积全量文本**做 `sanitizeOutput`（正则+split+逐行），输出越长越慢；
   这些都在 renderer 主线程，与 Agent 循环**同线程**。改：节流到 500ms + 只对增量 sanitize。
- **AGENT_SYSTEM_PROMPT 瘦身**：每轮全量重发（≈2600 中文字），规则越堆越多。
  有前缀缓存后收益打折，优先级低于第 1 条。
- 固定 sleep（`sleep(sawEnd ? 80 : 150)` + 60ms 轮询）每命令约 150~250ms，小头。
