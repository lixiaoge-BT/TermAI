# 2026-10-29 终端「偶发打不进字」定位与加固

## 症状
终端敲命令时偶发整个键盘失效：空格无效、字母进不去、退格改不掉已输入的字。
重启窗口才恢复。无规律、无报错、控制台干净。

## 定位（读 xterm 5.3.0 打包源码 + 探针，非猜测）
1. **输入法组合态卡死**（主因）
   - Chromium 在输入法处理期间给每个 keydown 填 `keyCode=229`。
   - xterm `CompositionHelper.keydown()`：`_isComposing` 为真时对 229 直接
     `return false` → `_keyDown` 提前返回 → **不产生 onData**，字节到不了 PTY。
   - `_isComposing` 只有 `compositionend` 能清；而 `_handleTextAreaBlur()` 会
     `textarea.value=""` 却**不复位 `_isComposing`**。组合途中失焦（侧栏抢焦点 /
     Ctrl+Space 切输入法 / ResizeObserver 里 fit 重排）→ compositionend 丢失 →
     之后所有键被吞且无法自愈。
2. **React 18 根级委托**收到 229 keydown 会再合成组合事件，和 xterm 自己挂在
   textarea 上的原生处理互踩（典型：组合块第一个字丢）。
3. **ipcRenderer.invoke 的 Promise 没人接**：主进程窗口未就绪时 reject → 按键
   静默丢弃，无任何日志，排查时看不出丢在哪一段。
4. **重渲染风暴**（加剧「打字要等一会儿」）：`XTerminal` 直接
   `useTerminalStore(s => s.sessions.find(...))`、`SplitView` 直接订阅 `s.sessions`
   → 每块输出都换 session 引用 → 每个终端组件随输出逐块重渲染。
5. **抢焦点**：AI 侧栏收到 `termai:quick-ask` 就 focus 自己的 textarea，而
   `tryAutoAnalyze`（报错自动分析）也派发同一事件 → 用户敲命令瞬间焦点被拽走。
   Ctrl+F 之前是**全窗口**响应，焦点在别处也会弹查找框抢焦点。

## 整改
- 新增 `src/lib/terminalInputGuard.ts`：textarea 捕获相拦 229（stopPropagation，
  但**不能挂在宿主元素上**——捕获相 stopPropagation 会让事件根本到不了 target，
  会连 xterm 自己的处理一起掐掉）；`229 keydown 但没有 compositionupdate 超过
  800ms` → 补发 `compositionend` 强行收尾；统计 imeKeydowns/dataEvents/
  stuckReleases，挂 `window.__termaiInputDiag()`。
  **只把 compositionupdate 当存活证据，不用 input 事件**——卡死时 Chromium 仍会
  零星派发 input，拿它续命会让自愈永不触发。
- `XTerminal`：删掉 session 对象订阅，按键时 `getState()` 实时读 status（顺带去掉
  `session?.status` 依赖，避免每次连接/断开重建 onData 订阅、空窗期丢键）；
  写失败打一次 warn；Ctrl+F 仅在本终端持有焦点时响应，关闭查找后把焦点还给终端；
  `focusTerm` 不再从任意可输入元素（含终端内查找框）抢焦点；`tryAutoAnalyze`
  派发前 `suppressAutoFocus(2500)`。
- 新增 `src/lib/uiFocus.ts`：自动唤起 AI 不抢焦点的抑制窗。
- `SplitView`：`useShallow` + `WeakMap` 缓存映射成 `{id,hostId,host,connected,status}`
  的小对象；`XTerminal` 用 `memo` 包一层。
- 探针 `dist-test/probe_input_guard.mjs`（7/7 通过，自己写假 textarea/Terminal，
  需 `globalThis.window={}` + `CompositionEvent` polyfill），单测
  `src/lib/terminalInputGuard.test.ts`（11 条）。

## 教训
- **探针自身的假事件对象会被 `{...ev}` 复制**，断言 `e.stopped` 要拿 `fire()` 的
  返回值，否则测的是原对象 → 假阴性。
- 统计类断言要扣掉探针自己挂的监听器个数。
- `src/services/ai.ts`、`agent.ts`、`store/agent.ts`、`package.json` 有**未提交的
  历史改动**；`ai.stream.test` 的「max_tokens 截断」那条失败来自它们，与本次无关。
  （当日稍后已修：该用例的预期过时了 —— 截断现在**不再当成功返回**，改为抛
  `OutputBudgetError` 触发「放大预算 + 关思考」重试。测试改成断言 rejects +
  「重试后成功」的正向用例，门禁恢复 380/380 全绿。）

# 2026-10-29 Agent 接管「能力差 / 一直分析 / 空总结」整改

## 截图实证症状
1. 「AI 正在分析并执行…」spinner 一直转，同时面板里已经躺着**上一轮**的「任务总结」
   → 续跑时 `isFresh=false` 不重置 `summary`，而 `phase="running"`，两者同屏打架。
2. 「任务总结」里只有一行 `<<<DONE>>>`，零正文。
3. 轨迹：`ifconfig` ✓ → `ip addr show -n` ✗ → 又 `ifconfig` → 又 `ip addr show -n`
   → `<<<DONE>>>`；4 步就触发压缩（8.3s / 49.5k tok）。

## 定位（探针复现，非推断）
1. **PLAN 吞命令**（`parseAgentReply`）：`<<<PLAN>>>` 分支先于 RUN 判定且
   `return commands: []`。模型把计划与首条命令写在同一条回复里（小模型高频）时，
   **整轮 RUN 块被丢弃**。探针：`PLAN+RUN 同轮 => cmds: 0`。run() 里 `if (parsed.plan) continue`
   又补一刀。→ 每轮白烧一次完整往返。
2. **空 DONE 兜底成总结**：`finalAnswer: after || before || raw`，raw 就是
   `<<<DONE>>>` 本身 → 总结卡片里只剩协议串。
3. **压缩触发过早**（条数 12 / 每轮 +2 条 → 第 6 轮就压）：压缩是**一次完整的大输入
   LLM 往返**且卡在主链路 await，还让滚动摘要逐轮衰减（模型忘事 → 重复探测）。
   同时 `MAX_AGENT_MESSAGES=14` 只比触发值大 2，`hardTrim` 每轮抢跑，压缩形同虚设。
4. **压缩调用用默认 120s 超时 + 2 次重试**：最坏白等 6 分钟且零进度提示。
5. **无收敛的截断循环**：截断轮不建 step、不耗步数预算，只靠 20 分钟总超时兜底。
6. **phase 死锁**：`phase==="running"` 就 `return`，一旦上次 run 在 finally 前被打断，
   phase 永远停 running → 按钮永久失效、界面卡在「正在分析」。

## 整改
- `services/agent.ts`
  - `parseAgentReply`：PLAN 分支额外解析其后的 RUN 块并返回 commands；DONE 的
    `finalAnswer` 去掉 `|| raw` 兜底（空总结留空，交上层打回）。
  - 单测新增 2 条（PLAN+RUN 保留命令 / 空 DONE 不把标记当结论），
    **都同时断言宽松判据仍成立**（纯 PLAN 仍无命令、有正文仍原样提取）。
- `store/agent.ts`
  - plan 分支：有命令时不 `continue`，直接执行首步。
  - 新增 `runningSessions: Set<string>` 同步锁替代 phase 判并发；入口发现
    「phase busy 但锁里没有」→ 判为残留态，重置为 stopped 后继续。
  - 压缩：`COMPRESS_TRIGGER 12→22`、`KEEP_RECENT 6→8`、`MAX_CONTEXT_TOKENS 24k→28k`、
    `MAX_AGENT_MESSAGES 14→30`；压缩调用 `timeouts:{totalMs:30s,idleMs:15s}`。
  - 空总结守卫：去掉 markdown 符号后有效字符 < 12 → 打回重写；连 3 次 → 用
    `executedLog` 台账兜底（不编造）。
  - 截断连击 ≥3 → 收尾并提示「调大 maxTokens / 换非思考型模型 / 网关是否支持
    enable_thinking:false」。
  - `syncExecLog(stepsUsed)`：把「已用 X/20 步、剩余 Y 步」写进 pinned 台账，
    让模型知道该收敛。
- `services/prompts.ts`
  - 修掉自相矛盾：头部说「立即输出 RUN/DONE」、规则 1 又说「第一轮必须先 PLAN」。
    现在明确「简单查询直接 RUN；复杂任务 PLAN 可与首个 RUN 同条回复」。
  - 新增规则 11：常用查询用最基础形式 + IP 速查（`ip -4 addr show` / `hostname -I`，
    点名 `ip addr show -n` 是无效参数 —— 截图里就是这么浪费两步的）。
- `components/AgentPanel.tsx`：busy 时总结卡片标「（上一轮的结论，新一轮仍在执行）」；
  spinner 加「本轮已等待 Ns」，≥60s 变警告色并提示可点停止。

## 补刀：把「一直在分析 / 总结为空」跑到实锤（无头循环探针）
搭了 `dist-test/probe/`：用 esbuild JS API + onResolve 插件，把真实 `store/agent.ts`
的 `run()` 打成 node 可跑的 ESM，只替换 6 个外部模块（AI 请求 / PTY 执行 /
config / terminal / 总线 / 回显过滤），其余（parseAgentReply、buildObservation、
dupTracker、各类准入检查）全用真实实现。入口 `node dist-test/probe/build.mjs`
→ `node dist-test/probe/loop.mjs`。

**探针抓到的真问题（此前纯读代码没看出来）**
1. **「只给计划」永不收敛**：`parsed.plan` 分支直接 `continue`，且顺手把
   `noMarkerStreak` 清零 → 只吐 `<<<PLAN>>>` 的模型一个计数都碰不到；
   「PLAN → 裸文本 → PLAN」还能互相重置对方的连击计数。
   实测：**201 次 LLM 调用仍在跑**，只能等 20 分钟总超时 → 界面就是「一直在分析」。
2. **孤立 `<<<PLAN>>>`（计划块为空）→ 总结里只剩协议串**：`plan` 为 "" 是 falsy，
   跳过 plan 分支；`done=false + commands=0` 掉进「直接收尾、summary 取 replyText」
   的分支。
3. 无限推进场景实测 22 次调用 / 20 步：多出的 2 次是**压缩调用**，
   探针按 `opts.timeouts` 是否存在区分「决策调用 / 压缩调用」，别混计。

**整改**
- `store/agent.ts`：新增「无进展」总闸门 `stalledRounds / lastSeenSteps /
  MAX_STALLED_ROUNDS=5` —— 只看「这一轮有没有真的落下一个 steps 条目」，
  与回复形态无关，兜住所有互相重置的分项闸门。命中后 phase=done + 台账总结。
- `store/agent.ts`：`commands===0 && !done` 的畸形回复不再当结论落盘，
  改为打回重写（交给无进展闸门收敛）。
- `services/agent.test.ts`：新增「孤立 PLAN 空块」用例，断言 done=false /
  finalAnswer=null / plan=""，并同时断言「有计划正文时仍识别为计划」。

**门禁**：tsc / eslint / vite build 全绿；`npm test` **381/381**；探针 **68/68**。
