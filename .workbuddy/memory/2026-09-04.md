## TermAI 内置 AI「不回复」故障 —— 根因与修复

**重要教训：一开始理解错了方向。** Brett 说"多问几个问题或者稍微让改动的就无法回复了"，
我误以为是 WorkBuddy 对话侧的 429 限流，跑去分析上下文膨胀；
 Brett 澄清"我刚才说的问题是我的终端"后才是真问题 —— **TermAI 内置的 AI 助手卡死不响应**。

### 根因：AI 请求没有任何超时保护

`src/services/ai.ts` 的 `requestChat()` 用 `fetch(url, { signal })`，
但 `AISidebar.tsx:426` 创建的 `AbortController` **只有用户手动点「停止」才会 abort**
（全局 grep 无任何自动 `setTimeout(() => abort())`）。

一旦请求挂起（服务端不响应 / SSE 流建立后不推数据 / 网络假死），
`await chatCompletion()` 永久 pending → UI 卡在 `setLoading(true)` + 空占位气泡
 → 用户感知「AI 不回复了」。

**两条挂起路径**：
1. `fetch` 本身不返回 → 无总超时
2. SSE 流已建立但服务端不推数据 → `reader.read()` 一直 pending → 无空闲超时

### 次因：终端输出只有行数上限，没有字符数上限

`buildContextBlock` 取 `recentOutput.slice(-80)`，80 行封顶，
但**每行长度无限制**。`cat` 大文件 / 编译日志刷屏时，80 行可堆到几十万字符
 → 请求体撑爆上下文 → 更容易触发超时或服务端拒绝。

这解释了「多问几个问题就触发」：终端操作越多，`recentOutput` 越臃肿，请求越大。

### 保护机制对比（关键证据）

| 保护 | Agent 模式 `store/agent.ts` | 普通聊天 `AISidebar → services/ai.ts` |
|---|---|---|
| 单次请求超时 | ❌ 也没有 | ❌ |
| 任务总超时 | ✅ 5 分钟（**但循环内检查，卡在单次 await 时无效**）| ❌ |
| 上下文 token 上限 | ✅ 40000 | ❌ |
| 上下文压缩 | ✅ `shouldCompress` | ❌ |
| 终端输出裁剪 | ✅ perBudget | ❌ 原样 80 行 |

注：Agent 模式的 `TASK_TIMEOUT_MS` 是循环内 `if (Date.now() - startedAt > ...)` 软超时，
**单次请求挂起时检查根本没机会执行**，同样救不了。

### 修复（2 个文件 + 3 个测试）

1. **`src/services/ai.ts`**
   - 新增 `createTimeoutSignal()`：合并外部 signal 与自动总超时（`REQUEST_TIMEOUT_MS = 120s`）
   - 新增 `readChunk()`：流式**空闲**超时（`STREAM_IDLE_TIMEOUT_MS = 45s`），
     比总超时更精准 —— 流已建立但不推数据时，总超时之前 UI 就已假死
   - 总超时覆盖「fetch → 读完响应」全过程（含 `resp.json()`）
   - `timeouts` 参数可注入，便于测试

2. **`src/services/prompts.ts`**

## 续：第二种症状「输入后完全没反应」——同一根因的另一个表现

Brett 补充：「我输入问题之后直接没有回复了，问题输入上去了，但是没有任何反应」。
注意这与前一种症状（转圈卡死）**看似不同，实则同源**。

### 症状差异的成因

发送按钮：`disabled={isLoading || !input.trim()}`（AISidebar.tsx:577）

| 时机 | isLoading | 用户看到 |
|---|---|---|
| 首次卡住那次 | 刚被置 true | 转圈动画在转，一直转（第一种症状） |
| 之后再提问 | **仍卡在 true** | 按钮已灰，点了毫无反应、无报错（第二种症状） |

所以「完全没反应」= 上一次请求把 `isLoading` 永久留在了 true，
按钮被禁用，**且没有任何提示告诉用户为什么点不动**。

### 本轮修复（AISidebar.tsx，3 处）

1. **loading 卡死守卫**（关键，保证永不死锁）
   `LOADING_STUCK_GUARD_MS = 150_000`（比 AI 请求总超时 120s 多 30s 余量）。
   isLoading 为 true 时起一个定时器，超时强制 `setLoading(false)` 并提示
   「请求长时间未响应，已自动恢复，请重试」。
   即便将来有别的路径导致 loading 复位失败，用户最多等 150 秒就能自救，不用重启。

2. **切换会话 / 卸载时中止进行中的请求**
   发现 `<ChatArea>`（AISidebar.tsx:144）**没有 key prop** —— 切换终端会话时组件不重建，
   `abortRef` 一直指向旧会话的 controller。后果：在新会话点「停止」会停错会话，
   旧会话的 loading 也可能残留。加了依赖 `chatKey` 的 cleanup effect 来 abort。

3. **并发竞态修复**
   - `send()` 开头先 `abortRef.current?.abort()`：快捷提示（QuickPill）是**直接调 send** 的，
     绕过 disabled 按钮，能在 loading 中再次触发，导致两请求并发写同一会话。
   - `finally` 改为**身份判断**后才复位：`if (abortRef.current === controller)`。
     原实现无条件 `setLoading(false)` + `abortRef.current = null`，
     先发起的请求结束时会把后发起的请求错误标记为已完成，并把新 controller 抹成 null。

### 🔴 HIGH — 渲染层 XSS（linkify 属性逃逸）
根因：`escapeHtml` 把 `"`→`&quot;`，随后 `linkify` 注入 `href="$1"`；HTML 解析器会把
属性值里的 `&quot;` 解码回 `"`，于是 `https://e.com?x=" onmouseover=alert(1)` 这类串
能打破 href 属性注入事件处理器。两个 sink 共享同一缺陷：
- `src/components/AISidebar.tsx:773` + `linkify()` @837：`dangerouslySetInnerHTML`
- `src/lib/markdown.ts:44-47`（被 `AgentPanel.tsx:522/539` 的 `dangerouslySetInnerHTML` 使用）
可达性：AI 回复（prompt injection）或构造的终端输出 → 渲染层执行任意 JS（能读 aiConfig 里的
API Key、终端内容、调用 preload 暴露的 ipc）。contextIsolation:true 但渲染层 XSS 仍危险。
修复：两处 URL 正则从 `[^\s<]+` 改为排除引号 `'"`，即 `(https?:\/\/[^\s<"']+)`（markdown 那处再加 `'`）。

### 🟠 MEDIUM
1. `XTerminal.tsx:484/538/568`：连接/重连后 `setTimeout(focus,150)` 未被追踪清理；
   unmount 后 Effect-1 已 dispose 终端，定时器仍 `term.focus()` 已 dispose 实例 → 控制台异常。
2. `store/agent.ts:221-265`：`run()` 在 224 行 guard 与 257 行 `set phase:running` 之间
   无 await，两次同步调用都会通过 guard，且 `abortRefs[sessionId]` 被后一次覆盖 → 前一次
   AbortController 成孤儿、stop() 只能 abort 最新的，Agent 任务可能关不掉/重复执行。
